# Demo Script

Phase 14 — a populated, realistic demo environment on top of the plain structural seed
(`prisma/seed.ts`: hostels, sports, venues, dummy Caretaker logins only). Run on demand,
never automatically, and built entirely through the real service layer
(`prisma/seed-demo.ts`) rather than raw inserts — every business rule (deadlines, approval
gates, bracket seeding, winner advancement, stock decrements) is enforced by the same code
the app's own HTTP API uses, so nothing here can be in a state the real app couldn't have
produced itself.

## Running it

```bash
cd backend
npm run seed:demo
```

It's idempotent against *itself* — if `secretary.demo@thapar.edu` already exists, it logs a
message and exits instead of duplicating everything. It does **not** touch any unrelated data
already in the database (your own earlier manual testing, old demo runs under different
names, etc.) — it only adds its own content on top.

### Getting a clean demo

For a presentation (vs. just adding demo content to whatever's already in your dev database),
reset first:

```bash
# from backend/, with the dev Postgres container running
docker exec playops-postgres-1 psql -U postgres -c "DROP DATABASE playops; CREATE DATABASE playops;"
npx prisma migrate deploy
npx prisma db seed    # base seed: hostels, sports, venues, Caretaker logins
npm run seed:demo     # this file's content
```

## Suggested walkthrough

A roughly 10-minute tour hitting every major feature, in an order that tells a story rather
than just clicking through menus:

1. **Sign in as the Hostel A Secretary** (`secretary.demo@thapar.edu`). The dashboard already
   has three tournaments at three different real lifecycle stages:
   - **Agira Football Cup** — *completed*. Open it: a full 4-team knockout bracket, both
     semifinals and the final all played, Agira Strikers crowned champions. Click into a
     match's scorecard to show real recorded goals, and the fixtures view to show the real
     scheduled venue/date/time each match was actually booked into.
   - **Agira Cricket League** — *completed*. Open Standings: a real points table (win=3,
     draw=1, loss=0) computed from three actually-recorded results, not hand-entered numbers.
   - **Agira Basketball Open** — *registration still open*. Open "View Teams": three approved
     teams, and **Agira Rookies sitting rejected** — a live example of the approval/reject
     flow with a real decision already made, not just an empty queue.
2. **Switch to the Sports Admin** (`admin.demo@thapar.edu`). Equipment page: a 5-item catalog
   with bookings in every real state — checked out, returned, rejected, and one still
   **pending** for you to approve live during the demo. Venue Bookings page: the same spread,
   plus one pending request waiting on a decision.
3. **Switch to a student** (`rohan.sharma@thapar.edu`). Their dashboard shows the notifications
   generated by the two announcements the Secretary posted (one hostel-wide, one tied
   specifically to the Football Cup) — a concrete example of FR-012 actually firing, not an
   empty inbox.
4. **Switch to the Hostel B Secretary** (`secretary2.demo@thapar.edu`) to make the tenant-
   isolation point explicitly: this dashboard only ever shows the Amritam Football Cup —
   Hostel A's three tournaments, its equipment bookings, and its students are never visible
   here, even though both hostels share the same running instance of the app.
5. **Log in as the Hostel A Caretaker** (`ACaretaker@thapar.edu` / `changeme123`) to close the
   loop at the top: this is who appointed the Secretary from step 1 in the first place (the
   Hostel Committee page shows that appointment as a real, already-made decision, not a demo
   stub).

## What this does *not* cover

- **Conflict detection & rescheduling (FR-009's auto-reschedule half)** — none of the seeded
  matches were cancelled, so there's no auto-suggested reschedule sitting in the UI to show.
  If you want to demonstrate that specific feature live, cancel any scheduled match yourself
  during the demo (as the Secretary) and show the real auto-search result instead of a seeded
  one — it's a more convincing demo live than it would be pre-baked anyway.
- **The hostel-change-request flow (FR-003)** — no student here has a pending request. Same
  reasoning: more convincing done live (sign in as any seeded student, request a hostel
  change, then switch to that hostel's Caretaker to approve/reject it) than pre-seeded.
